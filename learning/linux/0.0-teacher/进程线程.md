# 物理地址虚拟地址
***
基础知识: 程序数据存放在硬盘中, 运行时会放到内存中去运行
**内存的特点就是读写速度快.**

**程序: 存放在硬盘的可执行指令集合**
**进程: 程序一次执行的过程, 伴随资源的分配与释放**



## 为什么不能直接用物理地址?
***
早期的系统中, 没有虚拟地址, 所有都是在真实物理地址上操作.
只要空间被申请/使用, 就是合法地址, 未被申请/使用的地址就是非法的.
这就带来了一个问题, 就是**别的进程也可以获取其他进程的地址. **

由此带来了虚拟地址的概念, 由MMU统一管理,来识别进程地址的合法性.

## MMU
***
内存管理单元.
虚拟地址 物理地址的映射器.

特点:
1. 可以分配分散的物理地址映射成连续的虚拟地址
2. 判断地址的合法性
3. 当内存容量不够时, 可以调用一部分磁盘区域, 作为SWAP分区. SWAP分区就是把不经常使用的数据存放到磁盘中, 避免占用内存. 需要时再取到内存中去.

## 32位 64位
***
对应的是有多少根地址总线. (32根, 64根)

地址总线? 这是个新概念.
答: CPU想要访问内存某个位置, 就是需要告诉内存地址.
CPU和内存之间就有很多电路连接.用来传递"地址是多少"的线路组合, 就叫`Address Bus 地址总线`

32位的就是有32根电路组用作地址的传递.

## 引用计数
***
每通过文件描述符打开一个文件, 引用就会+1, `close`就会-1.

```markdown
Linux 中的“引用计数”可以理解为：**内核通过计数记录当前还有多少地方正在引用某个对象，以判断这个对象是否仍然需要存在。** 对于文件，需要区分不同层级的引用：目录中的文件名（硬链接）指向 inode，对应 inode 的链接计数；调用 `open()` / `fopen()` 打开文件后，会建立文件描述符、打开文件对象以及 inode 之间的引用关系；`fork()` 后，子进程复制文件描述符，会增加对同一个打开文件对象的引用。执行 `unlink()` 删除文件名时，只会移除目录项并减少 inode 的链接计数，如果文件仍处于打开状态，仍然可以通过已有的文件描述符访问它。当链接已经全部消失，并且相关的打开引用也全部释放后，内核文件系统就可以回收该文件占用的 inode 和数据块。**引用计数的核心思想就是：还有人引用，就继续保留；最后的引用消失，对象才具备被回收的条件。**
```

## 会话
***

一个抽象概念, 在终端中才有. 
我的理解: 你启动终端后, 终端默认启动了一个bash进程, 这个时候, 就有了一个会话,而默认启动的bash进程就是会话组id组长了, 后面执行命令, 程序而产生的进程, 都是在这个会话里面了, 所以它的组id也就对应bash的进程id.

**AI推荐记忆**
```markdown
Session 会话，是 Linux 内核用于组织和管理一批相关进程的抽象概念。一个 Session 可以包含多个进程组，一个进程组又可以包含多个进程。
在交互式终端中，Shell 通常处于一个 Session 中，并负责作业控制。Shell 启动的命令通常仍属于同一个 Session，但不同的作业可以被划分到不同的 Process Group 中。因此，同一个终端里运行的 bash、前台程序和后台程序通常 SID 相同，而 PGID 不一定相同。
Session 经常和终端一起使用，但 Session 本身并不依赖终端存在。setsid() 可以创建新的 Session，这也是守护进程脱离原控制终端的重要步骤。
```

## 进程组
***
进程组在我的实际应用中, 就只有在创建父子进程中会出现, 父子进程一般同属于一个进程组, 还有别的场景吗?

```markdown
**进程组 Process Group，是 Linux 为“一批需要统一进行信号和作业控制的进程”提供的分组机制。**

`fork()` 时子进程会继承父进程的进程组，所以简单的父子进程经常处于同一组。但 Shell 会主动创建和调整进程组，把一个 Job 中的进程组织在一起。尤其是管道命令，虽然涉及多个进程，在用户看来却是一个完整任务，因此很适合用一个进程组统一管理。
```

## 守护进程
***
```markdown
Linux 把进程组织成 Session → Process Group → Process。Session 像办公室，Process Group 像工作小组，Process 像组员。一个任务涉及多个相关进程时，可以把它们组织进同一个进程组统一管理；多个进程组又属于同一个会话。传统守护进程调用 setsid()，可以理解为离开原办公室，建立自己的新办公室，同时脱离原控制终端。
```

## 创建守护进程流程
***
### `fork` 一个子进程, 然后退出父进程(fork, exit)
❌️`fork`原因: 不能是一个进程组的组长, 不然会把进程组的其它无关进程带过去.
原因: `setsid`规定了: 调用该函数不能是进程组组长.和上面的原因没啥直接关系.

`exit`原因: 
子进程创建成功后, 就退出父进程, 让其成为孤儿进程, 然后被进程1收养.
此时`ppid`会发生改变, 具体的`ppid`看系统的实现.
但此时 `pgid` 和 `sid` 还是没变.

### `setsid` 新建一个会话, 脱离原会话
一般是终端(因为我们一般运行程序, 都是通过终端, 也可能有别的方式,但本质就是脱离原会话)
此时当前进程, 成为了会话的`leader`, 同时`pgid` 也会同步修改.

通俗点理解就是:  你的组长虽然走了, 但是你的组员身份还是没变.你的办公室也没变.
只有你换了办公室, 你的团队也会改变.

### `signal`函数忽略`SIGHUP`信号
`SIGHUP`信号: `hang up`挂断, 终端退出后, 所属的进程会收到这个信号, 默认操作是退出进程.
守护进程, 明显不应该受到这个信号的影响, 所以通过`signal`函数来**忽略**这个信号
`signal(SIGHUP, SIG_IGN)`

### `fork`出一个子进程, 父进程退出. 
目的: 彻底摆脱终端的控制
session leader有可能重新获得控制终端
例如在进程运行过程中, `open`了一个终端文件`\dev\tty\1`, 那么内核的一些判断机制, 可能会让这个进程控制这个终端, 因为它是session leader

这个操作就是让这个进程,彻底失去终端控制.

### `chdir`修改当前进程的工作目录
***
修改工作目录,是因为守护进程会一直运行, 如果一直占用某个特定的目录, 那么如果有卸载这个目录的需求, 就会失败, 因为一直在占用着这个目录.
而根目录是不会有卸载需求的, 会随系统的运行一直存在.

### `umask`修改文件掩码
***
从父进程继承的文件掩码, 可能属于某个用户的权限, 但守护进程是系统级别的, `umask`属于用户级配置, 不能受它的影响, 所以就重置`umask(0)` 想给它什么权限就什么权限.

***
`close(0) close(1) close(2)`

## `exit` `_exit` `return`
***
引入进程后, 现在遇到报错, 也会使用到`exit` `_exit`这俩函数了. 看效果和`return`一样. 它们是什么关系呢?

```
main() 里的 return
        ↓
    exit()
        ↓
做一些用户态清理工作
        ↓
    _exit()
        ↓
进入内核，真正终止进程
```

但这只是在`main`函数中, 在其它普通函数里, 就是返回到函数调用的位置去了. 但是在普通函数调用`exit`, 就会让进程退出.

## `signal`
***
信号处理函数
`signal(SIGNUM, sig_handler)`
指定信号值, 后面参数接一个处理函数

**处理函数要求**
内部不能使用异步的函数,典型是: `printf`, 这种有缓存机制的, 会导致下一个信号发生时被打断
```
主程序 printf()
    ↓
正在修改内部缓冲区
    ↓
    ← SIGINT 突然到达
    ↓
sig_handler()
    ↓
又调用 printf()
```

**如果有同一个信号同时进入信号队列, 会打包成一个发送给处理函数**
![[file-20260923111958891.png]]
这么写来避免信号同时发送导致的有些信号未被处理.

# 线程
***
一个进程至少有一个线程, 被称为主线程.
在C程序里, main函数就是主线程(main thread)
线程没有父子关系, 都是对等线程.

主线程先运行, 其他的线程运行顺序未知.

## 回收
***
没有父子关系,所以任意一个线程都可以回收. 
回收函数: **`pthread_join`**
线程只有两个属性: 结合态(`join`) 分离态(`detach`). 默认是结合态

## 属性设置
***
### 在`pthread_create`时设置
***
通过`pthread_attr_t` `pthread_attr_init` `pthread_attr_setdetachstate` `pthread_attr_destroy`等函数设置
**比较麻烦**

还有一个缺点:
create的时候设置成分离态, 就会有概率获得已经释放的`tid`
流程如下: 
```
pthread_create -> detach -> 执行剩余代码 -> 返回tid 
					|
					线程执行 -> 线程执行完毕 -> 线程已销毁
```

### `pthread_detach` 设置
